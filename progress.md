## 1a. Submission folder and 50 test seeds — 2026-09-23

Evaluation now uses **50 unseen test seeds** (`test_seeds` = `paper_seeds` in
`uno_predict.py`). The original ten come first and the other forty were drawn once
from [20000, 100000) with a fixed generator, excluding every tune seed, and
written out literally so the list never changes.

`make_submission.py` builds `Submission/` in the layout of the example folder:
per composition and per box size, `snapshots_*.png` (no R² panel),
`psi_distribution_*.png` (P(ψ) at t = 2000, truth magenta, prediction blue, all
seeds pooled) and `domain_growth_*.png` (truth, prediction and the
Lifshitz–Slyozov t^{1/3} law), plus `sweeps.png`, a `manifest.json` per run and a
`README.md`. No existing file in `Results/` is modified; `--rollout` only adds
ground truth for new seeds to `Results/cache/` (320 files, 16 GB for the forty
new seeds).

- **Two stages.** `--rollout` loads the checkpoint and caches, per seed, R²(t),
  L(t) for truth and prediction, and the snapshot frames in
  `result_cache/train_t300/`. The plain call draws everything from that cache in
  ~10 s with no model loaded.
- **Runs are views of a cache.** A = the first 10 seeds, B = all 50, C = the
  t = 500 model on 50. A is therefore a subset of B by construction, and a cache
  refuses to mix checkpoints (sha256 fingerprint).
- **Verified:** run A reproduces job 399765's documented R²(2000) on every
  composition to within 6.1 × 10⁻⁷ on the means and 4 × 10⁻⁶ per seed (MPS
  against CUDA float noise).
- **Box sizes now use the critical quench's own tuned schedule.** In
  `uno_predict.py` the box sweep inherits whichever schedule the last quench
  tuned (ψ₀ = +0.4's), so its l = 128 curve is not the critical quench. The
  submission fixes that, so `*_l128.png` is exactly `*_psi0p0.00.png`. `Results/`
  and README §3's box-transfer table still use the old behaviour.
- **L(t) is Puri's definition** (ch. 1, Fig. 1.7): the distance over which C(r,t)
  falls to half its maximum. The manifest also records the exponent from the
  zero-crossing length used in `Results/`; the two agree on every truth-vs-UNO
  gap to within ~1.5 percentage points.
- **The growth-exponent agreement is weaker than README §3 says.** That table's
  0.3082 vs 0.3107 (+0.8 %) comes from `figure_physics`, which fits a **single
  seed**. Over run B's 50 seeds the UNO's exponent is **+5.9 %** high at the
  critical quench (0.301 truth, 0.318 UNO; +6.0 % by the zero-crossing length) and
  **+9.0 to +9.3 %** at the transfer boxes, while the off-critical quenches sit
  within ±3 %. L(t) tracks truth within ~2 % to t = 1000 and over-coarsens after.
- **B's headline numbers** (R² at t = 2000, mean over 50 seeds): 0.776 / 0.766 /
  0.788 / 0.759 / 0.774 for ψ₀ = −0.4 … +0.4, and 0.784 / 0.759 / 0.752 at
  l = 160 / 192 / 256. The A/B mixture composition is unchanged to five
  decimals on every case, and the UNO's fraction of A-rich sites at t = 2000
  matches the truth's to ≤ 0.32 percentage points. (Both sit up to ~1.9 points
  off the equilibrium lever rule at the off-critical quenches: that is the truth's
  own curved interfaces at t = 2000, not a model error.)
- **A → B is sampling, not the model.** Each composition moves by at most 0.032,
  about one standard error of a 10-seed mean.

New ground truth is solved by `ground_truth_batch` in `uno_train.py`, which
batches trajectories and is bit-identical to one-at-a-time solves (the Laplacian
now rolls the last two axes). All ground-truth writes are atomic, so a job killed
mid-write cannot leave a truncated file that later runs treat as cached.

## 2. The dataset is now generated on the GPU

`ch.py` has been replaced by **`ch_gpu.py`** (batched torch float64), on the
advisor's suggestion that if training and prediction run on the GPU the dataset
should too. 25 trajectories in 15.8 s on an A100 (job 399764). For scale, the equivalent
vectorised numpy loop takes ~1–2 min for the same 25 trajectories on this laptop;
how long the advisor's original `ch.py` took was never recorded.

**It is a faithful replacement, and this was checked rather than assumed** — with
one honest limitation: `ch.py` is no longer in the project, so the reference is
`_chc_np` in `ch_gpu.py`, an in-file transcription of `ch.py`'s loop, not the
advisor's own file. Keep a copy of `ch.py` if that distinction ever has to be
defended. The built-in `--verify` was never run in the job, so the shipped
`test.npz` was instead compared against that numpy path on trajectories 0, 10 and 19:

- float64 max|diff| **2.2e-13** over 30,000 steps — CUDA FMA contraction, not an
  algorithmic difference;
- after the float32 cast `build_cache` applies, **10 of 12,247,040 values** differ,
  each by one ULP;
- ⟨ψ⟩ identical to all 17 digits.

The frame algebra matches too: `integrate` keeps `ch.py`'s `data[j*gap]`, and
`features_labels` reproduces `prepare_features_labels` exactly for `START = 0` with
`GAP` dividing `N_AHEAD` — and the code raises if either assumption is broken. So
the data stays comparable with the other three architectures. `python ch_gpu.py
--verify 3` puts a check on the record, but note it regenerates trajectories 0–2 on
the GPU and compares those — it does not read the shipped `test.npz`, so it validates
the code path rather than the file.

First run on this dataset shows no regression: mean 0.8962 against the previous
0.8906, bias −10.6/−14.2 against −11.4/−17.1.

## 3. Established by measurement

- **There is no intrinsic predictability limit.** Perturbing truth at t = 100 by
  1e-4 / 1e-3 / 1e-2 and integrating exactly gives R²(2000) = 1.00000 / 1.00000 /
  0.99998. Coarsening is strongly contracting, so all rollout error is systematic
  model bias, not chaos.
- **One-step accuracy and rollout stability fight each other**, so selection runs a
  real 128-box rollout to t = 2000, not a one-step proxy.
- **R² alone cannot detect a broken conservation law — it rewards breaking it.**
  The `conserve_mass=False` ablation *improved* mean R² by +0.017 while drift went
  from ~1e-8 to ~1e-1, free energy stopped being monotone on 2 of 5 quenches, and
  ψ₀ = +0.4 broke badly. Only the physics panels reveal it. This is the strongest
  result for a presentation. README §3e.
- **Precision does not matter.** fp32 and fp64 peaked at the same epoch with the
  same val1 and landed 0.0017 apart against a standard error of 0.012. fp64 costs
  ~1.8× the wall time.
- **`end = 300` caps training at L ≈ 14.7 while the test needs L ≈ 27**, and the
  coarsening bias tracks L rather than t. Raising `end` is the highest-leverage
  change available — but it breaks the shared-dataset rule unless all four of us do
  it, so it needs the advisor's agreement.
  - Checked whether a 64-box can even supply useful long-time data: solving the
    exact dynamics on 64/128/256 boxes to t = 2000 (3 seeds), the 64-box tracks the
    256-box to within **3.4 %** by the real-space zero-crossing measure. It is *not*
    grossly finite-size contaminated. A −20 % gap appears in the `moment` estimator,
    but that is the estimator running out of k-resolution on a coarse grid, not
    physics — the `moment` estimator is sound at l = 128, where `diag_drift` runs.
  - Residual concern: only ~2.4 domains across the box at t = 2000, so per-snapshot
    statistics are thin. An argument for more trajectories, not against the change.

Every setting lives in the `CONFIG` dicts at the top of the Python files, so a run
is reproducible from those files alone. Report material goes to
`Results/<label>/` (label `train_t<END:04d>_pred_t<T:05d>`). Checkpoints, datasets,
the ground-truth cache, rollout caches and logs go to `Work/`. README §6 has the
full tree.

`Results/<label>/report.txt` is a plain-text model card written for every run
(by `make_submission.py`, from the rollout meta and `results.json`): architecture
and parameter count, checkpoint-selection metrics, the training configuration (20
selected keys, not the whole dict), the **A/B mixture composition at the start and
end of the rollout** with the shift in percentage points, and the solve time
against the ground-truth solver. The archived Sep 8 report predates the composition
table.

Panel (f) of `phase_ordering_kinetics_<case>.png` is the seed-mean **mean order
parameter vs. time** — ground truth
against prediction, with a right-hand axis in percent of material A, and the final
composition of both in the title. ψ is the composition contrast of the binary A/B
mixture, ψ = c_A − c_B with c_A + c_B = 1, so c_A = (1 + ψ)/2. Cahn–Hilliard conserves
⟨ψ⟩, so the composition at the end of the rollout must equal the one it started from.

## 5. What to do next

**Laplacian output (2026-10-07), the next experiment.** The analysis in
`Work/analysis/t1000_failure_2026-10-06/` showed every base model steps the 8
longest-wavelength Fourier modes of the l = 128 box (k = 0.049–0.069, below the
l = 64 training box's fundamental 0.098) 2.4–3.5× too far, and collapses there
after t ≈ 2000; the newest runs (all retrained with survival selection, predicted to
10000) show growth exponents 0.38–0.91 against a truth of 0.27–0.35, and R²(10000)
falls as END grows. Fix: the head predicts M and the increment is the periodic
5-point Laplacian of M (`CONFIG["laplacian_output"]`, `--variant lap`, the default).
The solver's update over any Δt is exactly ∇²₅ₚₜ of a summed M, so this is a change
of variables, not an approximation; it forces the factor −k² into every mode's
increment (the unseen low-k shells are damped by (k/k_min)² = 0.25 and 0.5), and it
conserves mass exactly. Damping those 8 modes by 0.4 after the fact lifted R²(5000)
from −0.15 to 0.84, so the k² factor should give damping of that size without
tuning. Risk: ∇² amplifies grid-scale noise in the head output by up to 8×; watch
interface sharpness and the early epochs. New low-k diagnostic: the teacher-forced
increment gain per wavenumber shell (`uno_predict.py` `diag_lowk`, `report.txt`
section 6; also `lowk g` in each training validation line). Measured on the base
END = 500 model: lowest shell 2.28–2.54 at t0 = 500 / 1000 / 2000 (a model that gets
the physics right has ≈ 1), first shell 0.89–0.91, mid 0.77, high 0.76–0.80.
Job order: retrain END = 300, 500, 1000 (and 2000) with `VARIANT=lap` (the default),
predict to 10000 (`utp.sh`), then `sp.sh`. The base runs stay in `Results/` for
comparison (labels without `_lap`; lap runs are `train_t<END>_lap_pred_t10000`,
shown as "Laplacian output" rows and curves). What it will not fix: the other
~20–25 % of the late-time error, the l = 128 box saturating (fewer than 4 domains
across after t ≈ 3400), and chaotic growth of small errors over long rollouts.
README §6 "Laplacian output" has the details.

**One experiment remains, and it is worth being honest about how weak the signal
is.** The five recorded test means are 0.9035 / 0.8883 / 0.8888 / 0.8906 / 0.8962 —
a total spread of 0.0152, so *all five*, the first included, sit inside a ±0.02 band.
The first run leads the current one by 0.0073, which is below the 0.012 standard
error on a 10-seed mean. It is not an established result that it is better.

Two things differ between it and the current configuration, not one: the curriculum
timing (unroll 4 from epoch 20 rather than 12) **and** the 5-seed selector (it used
5 validation seeds, everything since has used 10). Testing the timing alone leaves
the selector confounded. The timing variant:

```
unroll_stages = ((0.00, 1), (0.15, 2), (0.32, 4))   # unroll 2 from ep 10, 4 from ep 20
epochs        = 60
patience      = 0
```

If it lands near 0.90 with bias about −8 %, the late transition is worth keeping. If
it lands near 0.89, the schedule is converged and the first run was noise. Either way
the coarsening bias is the better discriminator: it is a teacher-forced per-step
measurement, far less noisy than a 10-seed R² mean.

Four traps to clear first — all verified against the code:

1. **`patience` is not in the resume stamp.** The stamp is `epochs`,
   `steps_per_epoch`, `lr`, `unroll_stages`, plus (since 2026-09-29) `train_shape`,
   `val_shape`, `npz` and `val_t1`. Editing `patience` alone leaves the
   completed state valid, and the run exits with "nothing left to train" while
   reporting the old best as if it had just trained. The new log must say *"training
   schedule changed … starting fresh"*.
2. **`patience = 4` is risky under this schedule.** The no-gain counter has no stage
   awareness, so a plateau during the longer unroll-1/2 phase can stop the run before
   unroll 4 begins. Keep `patience = 0`.
3. **Keep it away from the t300 model folder.** It is END = 300 again, so it
   would train into `Work/models/train_t0300/`, and a fresh start there moves the
   production checkpoint and state aside (to timestamped `_prev` / `_stale` names,
   so nothing is overwritten, but `uno_ch_best.pt` is no longer the model the
   t0300 rollout cache was built from). Give it its own
   `run_name` in `uno_train.py` (the files become `<run_name>_best.pt` and so on)
   and pass `--ckpt` to `uno_predict.py`. The run label is still
   `train_t0300_pred_t10000` (or `train_t0300_pred_t02000` with `--t-end 2000`), and
   an experiment checkpoint used with an existing label no longer stops: the rollout
   engine moves that label's `Work/rollout_cache/`, `Work/predict/` and `Results/`
   folders into `Archive/superseded/<label>_<oldfp>_<time>/` (read the
   `[superseded]` log lines; move them back to undo). Use a different `--t-end` to
   avoid that. There is no label override yet. The ground-truth cache is shared,
   so the experiment costs no re-solving.
4. **Stage arithmetic** is `epoch >= 1 + int(frac * epochs)`, so those fractions give
   unroll 2 from epoch 10 and unroll 4 from epoch 20.

Offered but not started: a t = 5000 breakage test, and a semi-implicit spectral
solver so the speedup claim has a fair baseline.

## 6. What not to trust

- **The 0.80 stop rule is not implemented as written.** The advisor asked for the
  rollout to stop once R² drops below 0.80; this runs the full horizon and reports
  the crossing time instead. The truncated answer **cannot** be recovered from the
  saved output: `results.json` keeps the crossing time and a few sampled R² values,
  never the full R²(t) array, so re-deriving a truncated score needs a re-run. The
  rollout figure no longer plots a whole-horizon mean, but `r2_mean` in the JSON is
  still averaged over the whole 1900 **including the part below threshold**. State
  the deviation explicitly, or add a truncating mode.
- **Every job so far ran Python 3.11.7, not the 3.12 the advisor asked for.**
  `env/pyvenv.cfg` records `version = 3.11.7`, and every job script does
  `source env/bin/activate`, so the `module load python` line is irrelevant — the
  venv decides. Until 2026-09-29 no script echoed a version, which is why this
  went unnoticed; all five jobs now print `python --version`. Rebuild the venv on
  3.12. This is a real requirement, not a formality:
  a 3.12-only f-string once killed a job after the queue wait, and `pyright` does
  not catch that class of error.
- **The speedup figure is unstable.** Three measurements of the same quantity on the
  same A100 gave 96× / 56× / 67× like-for-like. The stride tuner picks a different
  number of steps each run (51–66) and per-step time varies ~33 % between nodes.
  README now quotes 67×; `presentation_notes.md` still says "roughly a hundred times
  faster" and should be brought down.
- **Three of the five runs have artifacts here; two do not.** `uno_ch_train.log` and
  `uno_ch_predict.log` are both append-mode and each holds three runs, so the
  2026-08-23 run (val 0.8891, test 0.8906) and the 2026-08-25 `conserve_mass=False`
  ablation (val 0.9262, epoch 20) are both re-derivable from those logs (after the
  migration: `Work/models/train_t0300/uno_ch_train.log` and
  `Archive/Results_2026-09-08/uno_ch_predict.log`) alongside job 399765
  (`Archive/Results_2026-09-08/a100_job399765/`). Only the two fp64 runs left
  nothing behind.
- **The ablation checkpoint is not lost.** `uno_ch_best_prev.pt` (was `Results/`,
  now `Work/models/train_t0300/`) *is* it —
  `conserve_mass=False`, rollout 0.9262, epoch 20 — rotated aside when the next run
  started, with its optimiser state in `uno_ch_state_stale.pt`. Only its *figures*
  are gone, so regenerating them is a prediction run against that checkpoint, not a
  retrain.
- **Fixed 2026-09-29: `--smoke` no longer falls back to the production
  checkpoint.** It loads only `Work/smoke/models/train_t<END>/uno_ch_best.pt` and
  writes only under `Work/smoke/`.
- **Both `uno_ch_train.log` (now `Work/models/train_t0300/`) and `uno_ch_predict.log`
  (now `Archive/Results_2026-09-08/`) are append-mode**, and each currently holds
  three runs. The ablation's numbers sit in
  the middle block of each, which makes them easy to quote by accident as if they
  were the current model's. Check the timestamp before quoting from either.
